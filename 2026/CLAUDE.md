# CLAUDE.md (2026 classic track)

This folder holds the **parked 2026 classic track**: the roboRIO / WPILib 2026 / Commands V2 version of the course, moved here from `docs/lessons/` and `code/` on 2026-11-12 so the OpMode (v3) track could become the course. **It is no longer maintained. Don't edit anything here unless the user asks.** The root [CLAUDE.md](../CLAUDE.md) covers the repository as a whole and the OpMode track.

The notes below are the classic-only material from the old root CLAUDE.md, moved here verbatim. Only paths were adjusted, so every path in this file is relative to this `2026/` folder (`lessons/`, `code/`, `tools/`), and commands run from the repository root as `./2026/tools/verify-lessons.sh`. Where a note says "both tracks" or "the OpMode track", it was written when the two lived side by side; the OpMode track is at `docs/lessons/v3/` and `code/v3/` in the repository root. The classic lessons, plan docs and reference code are described in [README.md](README.md).

## What is in this folder

There is Java here, though, in two forms under `code/`:

- **`code/lesson-N/`** — a per-lesson reference snapshot holding *only the files that lesson changes*, mirroring the `frc/robot` package layout (root classes at `code/lesson-N/`, subsystems at `code/lesson-N/subsystems/`, commands at `code/lesson-N/commands/`, deploy assets at `code/lesson-N/deploy/`). These are reference copies, not a buildable project.
- **`code/ActualLessons/`** — a real, buildable GradleRIO project: **the students' starting point**, held at pristine WPILib Command Robot template state (byte-identical to the upstream template, only `WPILibNewCommands` in `vendordeps/`, since Phoenix 6 is installed by Lesson 1 and everything else later). Students clone it and work forward from Lesson 0. **Keep it at baseline** — do not roll lesson work into it, and do not add vendordeps a lesson hasn't reached yet.

## Verifying lesson code

**`./2026/tools/verify-lessons.sh [N] [test] [aside-<slug>] [--base PATH] [--sandbox PATH]`** compile-checks the lessons for real. It copies `ActualLessons` to a scratch sandbox (never touching the repo copy), fetches pinned vendordeps, rolls `code/lesson-0` … `code/lesson-N` forward in order, replays the deletions the lessons instruct, appends Lesson 13's AdvantageKit `build.gradle` blocks, and runs Gradle. First run takes a few minutes to fill the Gradle cache; later runs are seconds.

**`--base` swaps the project the snapshots roll onto** (default
`code/ActualLessons`), so the same script can check a student's own repo:
`./2026/tools/verify-lessons.sh 7 --base ~/dev/MyRobot`. Pass `-1` to roll no
snapshots and fetch no vendordeps — that just builds the base as it stands.
The sandbox is `rm -rf`'d every run, so the script refuses a `--sandbox`
that names the base or anything inside this repo, and it drops the base's
`.git`/`build`/`.gradle` from the copy rather than building on stale state.
[README.md](README.md)'s "Skipping ahead to a lesson in the middle" section
points students at `--sandbox` for the other direction — generating a
keepable project in the state a lesson expects, so they can start mid-course.
Both flags also work as environment variables (`VERIFY_BASE`/`VERIFY_SANDBOX`)
for backward compatibility — a flag wins if both are given. Keep the two
scripts (`verify-lessons.sh` and `verify-lessons-v3.sh`) in sync if the
interface changes.

## Verifying and hard-won details

**Use it instead of reasoning about whether a snippet compiles.** Current state: lessons 0–34 all compile, at every intermediate stopping point, with zero warnings. A regression is therefore a real result, not noise. Run the specific lesson you touched plus the highest one.

For anything with runtime behavior — a JSON schema, a replacement for a deprecated API, a config with validation — drop a throwaway JUnit test into the sandbox's `src/test/java/` and re-run with `test`. That has caught things compiling never would.

Hard-won details worth not rediscovering:

- **Pin vendordeps to WPILib's marketplace**, `.../vendor-json-repo/main/<YEAR>/<name>-<version>.json` — one immutable file per version, with `<YEAR>_metadata.json` as the index. Do **not** cite a vendor's own "latest" link in a lesson. Two of the three third-party libraries here were actively broken through theirs at the same time: PhotonVision's served a next-season alpha whose manifest GradleRIO rejects outright, and maple-sim's advertised a version that was never uploaded to their Maven repo.
- A vendordep must be saved under the `fileName` declared **inside** the JSON, not the URL's basename — Lesson 13's `build.gradle` block reads `vendordeps/AdvantageKit.json` by that exact name.
- `code/lesson-N/deploy/**` maps to `src/main/deploy/**`, not into the Java tree, and **`code/lesson-N/tests/**` maps to `src/test/java/frc/robot/`** (added for L32; the main-source pass excludes `./tests/*` so those files aren't copied twice). `./2026/tools/verify-lessons.sh 32 test` therefore runs the lesson's own tests.
- Snapshots can only add or replace files, so **deletions live in the script**: `DriveModule` (L7), `ExampleCommand`/`ExampleSubsystem` (L9 §3), `VisionPoseProvider` (L15).
- maple-sim's jars exist **only** on `shenzhen-robotics-alliance.github.io` — not Maven Central despite being a listed fallback, not on `frcmaven.wpi.edu`, and not buildable via JitPack. That host must be reachable or Lesson 16 can't be verified. BLine's jars and sources come from `jitpack.io`.
- Reading a library's **sources jar** beats reading its docs. BLine's docs described an `EventTrigger` class you construct; it's actually a `FollowPath` static. Its sources/javadoc jars are on JitPack next to the main jar.

Target platform (assumed by every lesson): **WPILib 2026**, **Phoenix 6**, **TalonFX** drive/steer motors, **Pigeon 2** gyro, Xbox controller, **AdvantageKit** logging (from Lesson 3 on).

## Lessons are strictly sequential

Lessons 0–34 form a single build. Each one:
- Introduces the **smallest possible** set of new Java and robot concepts.
- Ends with a runnable result the student can see (sim, plots, or hardware).
- Assumes every earlier lesson has already been done.
- Ends with `Next: [Lesson N+1 — Title](0N+1-slug.md)`.

Consequences when editing:
- Changing a class name, field name, method signature, CAN ID convention, or constant introduced early ripples through every later lesson. Search the whole [lessons/](lessons/) tree before renaming anything.
- Do not forward-reference a concept that hasn't been introduced yet. If a lesson needs `MathUtil.clamp`, `Translation2d`, kinematics, etc., check the lesson where it's first taught (see the table in [lessons/README.md](lessons/README.md)) and stay within what the student has seen.
- The `SwerveModule` / `Drivetrain` refactor happens in [Lesson 7](lessons/07-four-modules.md) — before that the single-module class is called `DriveModule` and is itself a subsystem. Match whichever name the current lesson is at.
- Simulation is introduced in [Lesson 4](lessons/04-simulation.md); lessons 1–3 must not depend on sim plumbing.
- Telemetry is AdvantageKit-style logging, introduced in [Lesson 3](lessons/03-telemetry.md): every value goes through `Logger.recordOutput("SubsystemName/ValueName", value)` from the subsystem's `periodic()` — never bare `SmartDashboard.putNumber`. All numbered lessons now follow this style; the auto chooser in [Lesson 9](lessons/09-autonomous.md) uses AdvantageKit's `LoggedDashboardChooser`, and [Lesson 11](lessons/11-odometry-field.md) draws the robot by logging a `Pose2d` to AdvantageScope's Odometry tab, plus a `Field2d` widget for viewing inside SimGUI (`SmartDashboard.putData` for a widget is the one sanctioned SmartDashboard use; per-value `putNumber` is not).
- Steering gets a CANcoder from [Lesson 5](lessons/05-steering-p-control.md) on — much earlier than the rest of the advanced arc — because a real (non-simulated) chassis needs it to boot with correct wheel angles, and Lesson 7's 4-module chassis is the first lesson where that matters. `DriveModule`'s (later `SwerveModule`'s) constructor creates the `CANcoder`, applies a `CANcoderConfiguration.MagnetSensor.MagnetOffset`, then **primes**: `m_steerMotor.setPosition(m_steerEncoder.getAbsolutePosition().getValueAsDouble())`, seeding the motor's own relative counter once at construction (a one-time read — the sensor still isn't used for feedback beyond that). Lesson 5 uses a pretend 1:1 ratio (no gear multiply on the primed value); Lesson 7 pays that off alongside the real `25:1` gear ratio (multiply the CANcoder's wheel-side reading by `kSteerGearRatio` before seeding the rotor-side counter) and parameterizes it per corner — `cancoderId` and `magnetOffsetRotations` join `driveId`/`steerId`/`location` as constructor params, so every module-array call site from Lesson 7 on passes five args, not three; `DriveConstants` carries the per-corner CANcoder CAN IDs and magnet-offset constants alongside the drive/steer ports.
- The advanced arc changes earlier conventions in ways later edits must respect: from [Lesson 12](lessons/12-model-based-control.md) on, modules use Phoenix onboard closed loop (`PositionVoltage`/`VelocityVoltage`, `ContinuousWrap` replaces the wrap loops, and the old software `SteerConstants.kP` is retired). Lesson 12 also **replaces** Lesson 5's one-time priming with continuous remote-sensor feedback — it does not introduce the CANcoder (that's already in the file since Lesson 5/7) — so the constructor signature does *not* change again here; only its body does: the priming `setPosition(...)` call is deleted, and the steer `TalonFXConfiguration.Feedback` block sets `FeedbackRemoteSensorID`/`FeedbackSensorSource = RemoteCANcoder`/`RotorToSensorRatio` (the old `SensorToMechanismRatio` role, renamed because the ratio is now rotor:CANcoder) instead of `SensorToMechanismRatio` directly; the drive motor's config is untouched. In sim, the CANcoder needs its own `CANcoderSimState` fed every tick (mechanism-side, no gear multiply) alongside the existing rotor feed from this lesson on — priming never needed this (a fresh sim CANcoder defaults to `0`, which happened to match the physics model's own zero), but continuous reading does, or the simulated closed loop chases a signal that never moves. From [Lesson 13](lessons/13-io-replay.md) on, hardware lives behind `ModuleIO`/`GyroIO` (sensor values are *inputs* via `Logger.processInputs`; computed values remain *outputs* via `recordOutput`), and a `Constants.Mode` enum (`REAL`/`SIM`/`REPLAY`) picks one implementation per mode via a `switch` expression: `ModuleIOTalonFX`/`GyroIOPigeon2` (pure hardware, no sim code — `ModuleIOTalonFX` owns the CANcoder too, `protected` like the motors), `ModuleIOSim` (extends `ModuleIOTalonFX` adding the physics models, including the CANcoder sim feed, so Phoenix's simulated firmware keeps running the loops) / `GyroIOSim` (standalone, integrates the commanded rate, no hardware), and `new ModuleIO() {}` / `new GyroIO() {}` for replay. All sim plumbing lives inside the sim IO classes — `simulationPeriodic` is gone. [Lesson 14](lessons/14-pose-estimator.md) moves pose tracking out of `Drivetrain` into a separate `Localizer` subsystem that owns a `SwerveDrivePoseEstimator` and fuses a registry of `PoseProvider` implementations — `Drivetrain` (odometry, registered first, so it `implements PoseProvider` and exposes `getKinematics`/`getRotation`/`getModulePositions`) and a `VisionPoseProvider` second; `getPose`, `resetPose`, the `Field2d` widget, and the pose log all live on `Localizer` now (`Localizer/Pose`), and `RobotContainer` must declare `m_drivetrain` before `m_localizer` so odometry ticks first. [Lesson 15](lessons/15-photonvision.md) deletes `VisionPoseProvider` and gives vision the same IO-layer treatment `ModuleIO`/`GyroIO` got in Lesson 13, so it replays too. A new `VisionIO` interface (`updateInputs`, an `@AutoLog` inputs class holding a `PoseObservation[]` — `PoseObservation` is a `record` of timestamp/`Pose3d`/tag count) has two implementations: `VisionIOPhotonVision` (real `PhotonCamera` + `PhotonPoseEstimator`, multi-tag-first with single-tag fallback, `protected PhotonCamera m_camera` foreshadowing the subclass) and `VisionIOPhotonVisionSim extends VisionIOPhotonVision` (adds `PhotonCameraSim`, `extends`-onto-real the same way `ModuleIOSim` does). `PhotonVisionPoseProvider implements PoseProvider` owns a `VisionIO` + its `VisionIOInputsAutoLogged` and loops `estimator.addVisionMeasurement` over the logged observations — same `PoseProvider` contract, so `Localizer` itself doesn't change. Multi-camera sim needs no helper class or varargs: `VisionIOPhotonVisionSim` keeps a `private static VisionSystemSim visionSim`, lazily built by whichever camera constructs first, and every camera after that just calls `addCamera` on the shared field — the first teaching use of a `static` field in the course. `PhotonVisionPoseProvider` also carries a `public static makeCamera(name, robotToCamera, Supplier<Pose2d> poseSupplier)` factory that switches on `Constants.kCurrentMode` to build the right `VisionIO` — the same pattern as `Drivetrain`'s `private static makeModule`, just `public` because `RobotContainer` calls it from outside; `RobotContainer` itself only calls `PhotonVisionPoseProvider.makeCamera(...)` per camera, keeping IO selection out of the wiring class. `RobotContainer` declares `m_localizer` right after `m_drivetrain` — before the two camera fields, which are blank `final`s (`private final PhotonVisionPoseProvider m_frontCamera;`, no initializer) — and builds both cameras in the constructor body with `m_localizer::getPose` as the `poseSupplier` argument, once `m_localizer`'s own field initializer has already run; this avoids relying on lambda-capture-before-assignment tricks. Vision flows through `VisionIO`/`@AutoLog` like every other sensor, so it replays exactly. [Lesson 16](lessons/16-maple-sim-field.md) swaps the per-module `DCMotorSim` physics for maple-sim's rigid-body chassis, entirely inside `ModuleIOSim`/`GyroIOSim`: `Drivetrain` gains a `private static final SwerveDriveSimulation m_driveSim = createDriveSim()` that is **null outside `SIM`** (`SimulatedArena.getInstance()` throws on a real robot, so the null guard is load-bearing), only the `SIM` arms of the two mode switches read it, `GyroIO.setSimRotationRate` is deleted along with both call sites, and the arena is stepped once in `Robot.simulationPeriodic()` — the one sanctioned exception to "sim code lives inside IO implementations," because the arena is shared world state. It also introduces **ground truth** (`Drivetrain/SimulatedPose`), so estimated pose can be plotted against truth instead of faking slip with a `1.1` multiplier. [Lesson 17](lessons/17-bline-autos.md) replaces hand-composed autos with BLine path following: `Drivetrain` gains exactly two public doors — `getChassisSpeeds()` (kinematics run backward via `m_kinematics.toChassisSpeeds(states)`) and `driveRobotRelative(ChassisSpeeds)` (a deliberately narrow wrapper around the still-`private` `applyChassisSpeeds`, *not* a visibility change) — and `Autos.followPath(drivetrain, localizer, pathName)` assembles a `FollowPath.Builder` with three `PIDController`s whose gains live in a new `Constants.PathConstants` (`kTranslationP`/`kRotationP`/`kCrossTrackP`, all `1/s`, staying bare `double`s like every other gain). `PIDController` is first taught here, after five lessons of hand-rolled P control. Paths are JSON under `src/main/deploy/autos/paths/`, with a **mandatory** `src/main/deploy/autos/config.json` for global constraints; angles in those files are radians. Event markers are registered statically once — a private `Autos.registerEventTriggers()` calling `FollowPath.registerEventTrigger("shoot", command)`, invoked as the first line of `buildChooser` — and referenced from a path element by `lib_key`; BLine resolves the key at *runtime*, so an unknown one logs a warning rather than throwing. BLine ships in package `frc.robot.lib.BLine` — under the robot's own package root, not a vendor namespace. Lesson 17 also moves auto *selection* into `Autos`: `Autos.buildChooser(drivetrain, localizer)` assigns **one** `private static FollowPath.Builder s_pathBuilder` (per-auto builders are the anti-pattern, and sharing the `PIDController`s is safe because every `FollowPath` requires the drivetrain), which a `private static followPath(String pathName)` wraps so a path auto is one line and `new Path(...)` appears exactly once; and returns a `LoggedDashboardChooser<Supplier<Command>>` whose options are lambdas, so no auto is constructed at startup. `chooser.onChange(recipe -> s_selected = recipe.get())` pre-builds the selection — it fires while **disabled** (AdvantageKit polls dashboard inputs every loop with no enable gate) and fires for the **default** option on the first loop, so no monitor command is needed; `RobotContainer` keeps only the chooser field and `getAutonomousCommand()` returns `Autos.selected()`, which defaults to `Commands.none()` rather than null. The word "recipe" is reserved for `Supplier<Command>` in this lesson — describe drive-turn-drive as a *script*, not a recipe. [Lesson 18](lessons/18-elevator.md) opens the mechanisms half by repeating Lesson 13's spine verbatim on new hardware — `ElevatorIO` (`@AutoLog` inputs: height, velocity, **applied volts**) / `ElevatorIOTalonFX` / `ElevatorIOSim extends ElevatorIOTalonFX` (WPILib `ElevatorSim` in `DCMotorSim`'s slot, `simulateGravity = true`) / an `Elevator` subsystem with the same `Constants.Mode` switch. New control vocabulary: `MotionMagicVoltage` + `MotionMagicConfigs` (cruise velocity and acceleration, in *mechanism* rotations — `SensorToMechanismRatio = kGearRatio` makes those drum rotations, so `metersToRotations` divides by drum circumference exactly as the drive motors divide by wheel circumference), and the **full feedforward set** `Slot0.kG`/`kV`/`kA` with `GravityTypeValue.Elevator_Static`. **Every profiled mechanism in this course gets `kG`+`kV`+`kA` with `kP` as the trim — never `kP`+`kG` alone.** That converges, which is what makes it a trap: nothing looks broken while the student is taught that position control means reacting to error. A pure feedback loop can only make voltage by first allowing error, and the arithmetic is stated in both lessons: the elevator's 1.0 m/s cruise costs 9 V, which `kP = 20` can only produce from 0.45 drum rotations ≈ **7 cm of deliberate lag** (measured with `kV = 0`: 94.5 mm; with the model: ~23 mm). **Gains are computed, never guessed, and the lessons show the arithmetic.** Two Kraken X60 spec-sheet facts do all of it (**classic track; the OpMode track has used 6065 RPM and 7.157 N·m since alpha-8, see the alpha-8 notes above**): 6000 RPM on 12 V = 100 rot/s ⇒ **0.12 V per rotor rotation/sec**, and 7.09 N·m stalled on 12 V ⇒ **1.69 V per N·m at the rotor**. Then always: what the *mechanism* needs → ÷ gear ratio for what the *rotor* needs → × 0.12 (speed) or × 1.69 (torque). That reproduces every constant in the files (elevator 1.44/0.18/0.003, arm 6.0/0.25/0.055) and cross-checks against Lesson 12's `kDriveKV = 0.8` via 6.75 × 0.12. Don't use the kT/R/Kv-rad-per-volt form in lesson text — same answers, more machinery, and its free-current term shifts `Kv` enough to stop matching the files. Both IO layers log the profile's instantaneous setpoint (`setpointMeters`/`setpointDegrees`, from `getClosedLoopReference()`) — without it a student can only plot position against the *goal*, which is a step, so profile lag and tracking error are indistinguishable and nothing is tunable. Lesson 18 §3 names the three-way distinction (goal / setpoint / position) and §9 is the tuning procedure in model order, each gain with its own graph signature. **Try It sections that break a safety layer carry a sim-only callout** — zeroing or inverting `kG` and bypassing `clampToTravel` mean a dropped carriage or an arm driven into its stop on real hardware; Lesson 18 §9 additionally has a real-hardware tuning-safety callout. `kS` stays 0 (frictionless sim) and is named only in a callout. Lowering `kP` once the model is in place was swept and rejected — tracking got monotonically worse. **`kG` must be the real holding voltage** — mass × g × drum radius, divided by the gear ratio, converted through the motor's torque constant; for this course's constants that is `0.18 V`, verified in sim (a guessed `0.3` still converged, because `kP` silently corrected for it, which is exactly the bug the lesson teaches against). Travel limits are enforced by clamping the *goal* in `Elevator.goToHeight` (`MathUtil.clamp`), not the per-tick output — the lesson's one new Java idea. `goToHeight` ends with `.until(this::atGoal)`; the mechanism keeps holding because a Phoenix control request persists until replaced. [Lesson 19](lessons/19-mechanism2d.md) draws that elevator, touching only `Constants.java` and `Elevator.java`: a `LoggedMechanism2d` canvas, a `LoggedMechanismRoot2d` at the frame's base, and a two-link chain `m_carriage` → `m_effector` built with `append(...)` (which returns the child, so each is one statement). **Use AdvantageKit's `Logged*` mechanism classes** (`org.littletonrobotics.junction.mechanism`), *not* WPILib's `Mechanism2d` — they have an identical API plus a `Logger.recordOutput(String, LoggedMechanism2d)` overload, so the picture replays like every other output; `SmartDashboard.putData` stays reserved for Lesson 11's `Field2d`. There is no `Elevator` constructor: the drawing is fields, mutated in `periodic()` (`setLength` from `m_inputs.heightMeters`, `setColor` from `atGoal()`), and `recordOutput` must run **every tick** because it serializes current state. `getRoot` is doubles-only — the one genuine `.in(Meters)` unpack here — while the ligament constructors take `Distance`/`Angle` measures. The lesson's whole point is that `m_effector` is written once and never updated: it rides the carriage because it's attached, and Lesson 20 replaces it with a real arm while the two lines that move the carriage stay put. [Lesson 20](lessons/20-intake-arm.md) is the third mechanism on the same spine — `ArmIO`/`ArmIOTalonFX`/`ArmIOSim extends ArmIOTalonFX` (`SingleJointedArmSim` in `ElevatorSim`'s slot, plus a `DCMotorSim` for the roller)/`Arm` — and spends its attention on what rotating changes. **`GravityTypeValue.Arm_Cosine`** scales `kG` by `cos θ`, which *requires* the sensor to read zero with the arm horizontal; Phoenix's javadoc and WPILib's `SingleJointedArmSim` agree on that convention (θ from horizontal, CCW-positive), so nothing needs a sign flip — but a wrong zero makes `kG` fight the arm, which is why Lesson 21's homing follows. The gains are the same four terms as the elevator's, only `kG`'s *shape* changes; `kArmKG = 0.25 V` is computed the same way Lesson 18's was and verified against the plot: holding voltage tracks `kG·cos θ` at every angle, hitting exactly `0` at vertical and **flipping sign** past it. Unlike the elevator there are no conversion helpers — an arm's mechanism unit already is rotation, so `kMaxVelocity.in(RotationsPerSecond)`, `withPosition(Degrees.of(...))`, and `getPosition().getValue().in(Degrees)` do the whole job. **Soft limits** (`SoftwareLimitSwitchConfigs`, thresholds in mechanism rotations) are added *alongside* Lesson 18's goal clamp, not instead of it: the clamp is your code's opinion, the soft limit sits below your code and holds when the logic is wrong. The **roller is a second motor in the same subsystem** on plain `set(fraction)` — Lesson 1's control style, because "spin while held" has no setpoint — and `runRoller` uses `finallyDo` rather than `.until(...)`. The arm's ligament is `append`ed to **the elevator's carriage**: `Elevator` gains a one-line `getCarriage()`, `m_effector`/`kEffectorLength` are deleted, `ElevatorConstants.kCarriageAngle` names the carriage's 90° so `Arm.toDrawingAngle` can subtract it, and `Arm`'s constructor takes `Elevator` (so `m_arm` must be declared after `m_elevator` — a hard requirement now, not just tick order). [Lesson 21](lessons/21-limit-sensors.md) closes the blind spot the mechanisms half has carried since Lesson 18: a TalonFX's built-in encoder is **relative**, so `0.00` at boot means "counting started here," not "the carriage is down" — which silently shifts `clampToTravel`'s range and feeds `Arm_Cosine` a wrong `θ`. The fix is **homing**: `Elevator.home()` = `run(setVoltage(kHomingVolts)).until(this::atBottomLimit).finallyDo(...)`, open-loop via `VoltageOut` (the course's only use) because position is the thing being established, and `finallyDo` must kill the voltage *before* `setPositionMeters` and `m_goal`. Wiring is **derived, not asserted**: the roboRIO pulls DIO high, so a cut wire reads `true`; therefore "keep going" must be the reading that needs a working wire ⇒ normally-closed to ground ⇒ **`get() == true` is "at the limit"** and a broken wire fails safe. (This is the opposite of the `!get()` folklore — don't repeat it.) **The sim change is the teaching centre and must stay:** `ElevatorIOSim` feeds the encoder `truth − kSimStartHeight` (a relative encoder reports only movement since power-on) while `atBottomLimit` is computed from plain `truth` — encoder = belief, switch = fact. Do it by subtraction, *not* by `setPosition(0)` in the sim constructor: that needs a tick to propagate and gave intermittent boot readings. `Trigger` is generalized here — `new Trigger(m_elevator::atBottomLimit)` — and `rezeroAtBottom()` is `Commands.runOnce(...).ignoringDisable(true)` with **no subsystem requirement** on purpose, so a switch brush can't cancel the driver's motion. Current sensing is taught in §9 (120 A stalled, measured) but shipped only as `statorCurrentAmps` in the inputs; building it is Try It #3. §9 also states the rule of thumb: a mechanism moving under one turn should be measured absolutely (a CANcoder, as an arm can have), otherwise home it. **Testing trap worth not rediscovering:** a JUnit loop that steps `m_model.update(0.020)` but sleeps only 4 ms runs physics 5× faster than Phoenix's real-time simulated firmware, which looks exactly like a missing `kV` — sleep the full 20 ms before judging profile tracking. Phoenix sim devices are also keyed by CAN ID and outlive a test, so give each test its own IDs (and IDs must be ≤ 62). A `DigitalInput` holds its DIO channel for the life of the JVM and `HAL.shutdown()` does not free it, so a homing test has to be one sequential scenario with a single IO instance; `setPositionMeters` also needs two ticks before it reads back.

[Lesson 22](lessons/22-light-sensors.md) closes the course with a beam break that separates "the roller is spinning" from "a piece is in here." Its polarity is the **opposite** of Lesson 21's on purpose, and that contrast is the teaching beat: a limit switch stuck on "at the limit" only stops a mechanism, while a beam break stuck on "I have a piece" makes the robot move unasked — so this one reads `!get()`, and a disconnected sensor says "no piece." The rule to state is *ask what a stuck reading would make the robot do*, never a per-sensor convention. **`ArmIOSim` must not fake `hasGamePiece` off the roller** — that would make the simulated sensor a function of the exact thing the lesson says it's independent of. It uses maple-sim's `IntakeSimulation.OverTheBumperIntake("Fuel", Drivetrain.getDriveSim(), ...)` (`register()` is required; `startIntake`/`stopIntake` from the roller sign; `getGamePiecesAmount() > 0` is the sensor; ejecting calls `obtainGamePieceFromIntake()` and drops a fresh `RebuiltFuelOnField` ahead of the robot so the cycle closes). `Drivetrain` gained `public static getDriveSim()` so sim types stay out of `Arm`/`RobotContainer`. Verified: 68 rps of roller on a cleared field reads `false`. `Trigger.debounce(double)` is **rising-edge only** — it delays believing *true* and reports *false* immediately. It provably does nothing in this sim (maple-sim's capture signal is clean); say so rather than faking flicker, and let Try It #2 introduce it. The capture binding is `Commands.parallel(arm.goToAngle, elevator.goToHeight)` — two subsystems off one sensor reading. **Lesson 22 deliberately has no `Next:` link**; it ends with a course send-off, so adding a Lesson 23 means rewriting that ending, not appending to it.

[Lesson 23](lessons/23-leds.md) drives an `AddressableLED` strip from state the robot already has, and is the first hardware since Lesson 13 that deliberately gets **no IO layer** — the IO pattern exists to make sensor *inputs* replayable and a strip is write-only, so wrapping it would mean an empty inputs class and three identical switch arms. [Lesson 24](lessons/24-superstructure.md) pays off Lesson 23's closing promise with a state machine. `SuperstructureState` (in `frc/robot/subsystems/`) is the course's first **enum with a constructor, a field, and methods** — each of six constants (`UNHOMED`/`IDLE`/`INTAKING`/`HANDOFF`/`HOLDING`/`SCORING`) carries its `LEDPattern`, so `LedConstants` is renamed one-per-state (`kUnhomed`, `kIdle`, `kIntaking`, `kHandoff`, `kHolding`, `kScoring`, plus `kBlinkPeriod`). **Not named `RobotState`** — `edu.wpi.first.wpilibj.RobotState` is a real WPILib class and the collision is a nasty first compile error; the lesson says so in one callout. **The load-bearing split is legality vs. readiness, and later lessons must keep it**: `canGoTo` is an exhaustive `switch` *expression* on the enum — reads no sensors, never changes, and governs only what a **request** may ask for — while `Superstructure.periodic()` owns the automatic sensor-driven transitions and deliberately does **not** consult `canGoTo` (the state machine doesn't ask itself permission). The exhaustiveness is the teaching payoff: adding a seventh constant stops the build until you say what it can do, and the lesson has the student add `CLIMBING` to watch it happen. **`UNHOMED.canGoTo(anything)` is `false`** — the only exit is `periodic()` seeing `m_elevator.isHomed()`, which makes Lesson 23's LED priority structural instead of cosmetic and closes the hole where a button could declare the robot homed without homing it. `Superstructure extends SubsystemBase` but owns no motors and **requires nothing** (so a state request can't cancel a moving mechanism); the lesson frames it as the deliberate mirror of Lesson 7's "`SwerveModule` stopped being a subsystem" — *what makes something a subsystem isn't owning hardware, it's needing the scheduler*. **The guard rule**: a command bound to a *button* guards itself with `.onlyIf(() -> allow(...))` (`Command.onlyIf(BooleanSupplier)` is the one new decorator — returns `ConditionalCommand`, condition evaluated once at schedule time); a command bound to a *state* via `inState(...)` does not, because arriving there already means the machine said yes. `allow` logs refusals to `Superstructure/Rejected` — a refused request is indistinguishable from a broken button from the driver's seat. **`Commands.parallel` throws when two of its commands require the same subsystem**, so `requestIntake` is a *sequence* of `goToAngle` then `runRoller`; L22's parallel was legal only because it paired an arm command with an elevator one. Lesson 22's `.debounce(...)` moves off the `Trigger` into a plain `edu.wpi.first.math.filter.Debouncer` field now that the beam break is read in `periodic()`. **`Leds` no longer takes subsystems** (the user asked for this explicitly): `Leds(Supplier<SuperstructureState>)`, wired as `new Leds(m_superstructure::getState)`, importing neither `Elevator` nor `Arm`; `Leds/Showing` is deleted in favour of `Superstructure/State` (the `Enum` overload of `recordOutput`), disabled stays orthogonal as one `.breathe(...)` line, and the alliance colour is a real casualty — an enum constant is `static final` and can't know the runtime alliance — so it became Try It #1. `RobotContainer` declares `m_superstructure` after `m_elevator`/`m_arm` and `m_leds` after that; **no binding mentions a sensor any more**. Scope was held deliberately: drivetrain, autos, vision, homing, and the D-pad elevator overrides are untouched, with the D-pad's life outside the state machine called out honestly and left as Try It #4. **Testing trap:** a scheduler test is *vacuous* unless you enable the robot — `CommandScheduler.run()` cancels everything while disabled, so both halves of an `onlyIf` test pass for the same wrong reason; use `DriverStationSim.setEnabled(true)` + `notifyNewData()` + `DriverStation.refreshData()` and assert `!DriverStation.isDisabled()` first. Each new final lesson replaces its predecessor's send-off with a forward handoff, so **Lesson 33 is currently the one that ends with a send-off and no `Next:` link**.

[Lesson 25](lessons/25-path-events.md) makes autonomous overlap its work, and adds **no new Java** — it is composition the student already has, aimed at a problem they haven't solved. Three beats: Lesson 17's `Commands.print("Event: shoot!")` placeholder becomes a real `"intake"` command (`goToAngle` then `runRoller(...).until(arm::hasGamePiece)` — the `.until` is load-bearing, or the roller holds the arm for the rest of the match); hence both the `release` marker *and* a `.finallyDo(FollowPath::clearRotationOverride)` handback on every path recipe — the marker is the plan, `finallyDo` is the guarantee, because a cancelled auto never reaches its last marker and the override is `static`. `registerEventTrigger(String, Command)` is implemented as `CommandScheduler.schedule(command)`, so the event command runs *independently* and **an event command that requires the drivetrain cancels the path that fired it** (verified) — the lesson states the rule as "any subsystem except the one the path is driving". `t_ratio` on an `event_trigger` is a fraction of **its owning segment**, not the whole path. **`getRemainingPathDistanceMeters()` returns `0.0` before `initialize()`** — a sentinel indistinguishable from "arrived"; it is safe inside `Commands.parallel` with the path (the group initializes the path first, verified) and fires instantly if hoisted into a standalone `Trigger`, which is a callout and a Try It. This is the mirror image of the Lesson 20-22 sleep trap. [Lesson 26](lessons/26-drive-to-pose.md) pays off **Lesson 11's `driveToPose` sketch**, which was written, labelled "minimal", and then never called in fifteen lessons. The lesson splits getting somewhere into two stages and renames things to match: `Drivetrain.driveToPose` becomes **`alignToPose`** (short-range only), and `Autos.driveToPose(drivetrain, localizer, target)` is the two-stage composition — `Commands.sequence(generated path to a staging pose, alignToPose)`. **The teaching centre is that "arrived" is a decision, not a fact**: a P controller approaches asymptotically and stops only because a tolerance says it may. The L11 sketch's finish condition reads translation only, and the measured demonstration is brutal — placed on the target facing backwards it declares arrival on **tick zero while 176° out**. Measured comparison, (1,1) → (5,4) @ 90°: the sketch declares success at 3.02 s while **49.9 mm** out, needs **3.64 s** to genuinely hit 2 cm/1°, while two stages take **2.58 s** and land at **17.9 mm / 0.01°** — *both faster and more accurate*, which is the signature of having split the wrong problem. Stage two is three `PIDController` **fields** on `Drivetrain` (fields, not locals, because `atPose()` must read the error the last `calculate()` saw) with `setTolerance`/`atSetpoint`, plus `enableContinuousInput(-PI, PI)` on the theta controller — the last chapter of the angle-wrap story that ran hand-rolled `while` (L5) → `MathUtil.inputModulus` (L10) → `ContinuousWrap` firmware (L12). There is deliberately **no clamp** in `alignToPose`: its top speed is `kAlignP × kStagingDistance` (3.0 × 0.4 = 1.2 m/s), so it is slow by construction, and `desaturateWheelSpeeds` catches misuse. New Java is **building a `Path` in code** — `new Path(new Path.Waypoint(translation, handoffRadius, rotation))`. **A generated path is a single waypoint** naming only the destination, because it starts wherever the robot is; verified valid and it drives there from the current pose. **`withPoseReset` must never be applied to a generated path** — `getStartPose()` on a one-waypoint path returns *that waypoint*, so the reset teleports the estimate onto the destination. Hence `makePathBuilder` no longer applies it and there are two builders: `s_pathBuilder` (drawn paths, `.withPoseReset(...)`) and `s_generatedBuilder` (no reset). `Path.isValid()` needs no defensive call — `FollowPath.isFinished()` already checks it, warns, and finishes early; say so rather than adding a check that never fires. `PIDController.atSetpoint()` is `false` before the first `calculate()`, so `.until(this::atPose)` needs no reset. **`RobotContainer` now calls `Autos.buildChooser(...)` BEFORE `configureBindings()`** — the left-bumper alignment binding asks `Autos` to build a command, and the path builders are created inside `buildChooser`; the old order NPEs at startup. [Lesson 27](lessons/27-object-detection.md) makes the target something the camera found. New spine: `ObjectDetectionIO` (`@AutoLog` inputs holding a `Detection[]`; `Detection` is a `record` of **yaw/pitch/confidence — raw camera angles, deliberately NOT a field position**, because a position depends on the pose estimate and an IO layer reports what the sensor said, not what you concluded) / `ObjectDetectionIOPhotonVision` (filters on class ID *and* confidence, `protected PhotonCamera m_camera` as in L15) / `ObjectDetectionIOPhotonVisionSim extends` it / a `GamePieceDetector extends SubsystemBase` that owns the mode switch, converts angles to field positions, and picks a target. **Everything below is measured, not inferred — do not re-derive it.** `new VisionTargetSim(pose, model, int, float)` sets `objDetClassId`/`objDetConf` and leaves `fiducialID = -1`; the **3-arg `(pose, model, int)` sets `fiducialID` instead** and yields detections the class filter rejects forever — both compile, and the failure is silent. **Positive pitch in a `robotToCamera` `Transform3d` points the camera DOWN**, while `PhotonUtils.calculateDistanceToTargetMeters` wants pitch measured UP from horizontal, hence the minus sign in `toFieldPosition`; a negative computed distance means the camera is looking above the horizon and must be discarded. The conversion needs three frames in three lines (camera → robot via `rotateBy(robotToCamera rotation)` + translation, then robot → field via `rotateBy(robot rotation)`), and it only works because **a game piece sits on the floor** so its centre height is known — maple-sim's Fuel is a 15 cm ball (`REBUILT_FUEL_INFO`: radius 0.075 m) whose centre is ~8 cm up. The sim IO needs its **own `VisionSystemSim`** (a camera belongs to exactly one, and L15's holds a static tag layout) and rebuilds its target set from `SimulatedArena.getInstance().getGamePiecesPosesByType("Fuel")` **every tick**, because pieces move. **Open decision 3 resolved as two constants, not an enum** — `kGamePieceType`/`kGamePieceClassId` — with the lesson stating that there is no standard class ID: it is the class index of the model you trained. New Java is **`Commands.defer(Supplier<Command>, Set<Subsystem>)`**, which is the whole reason the lesson works: every other command is built at startup, when nothing has been seen, so the approach path has to be built at schedule time; requirements must be declared up front because the command does not exist yet. `Autos.fetchPiece` composes `defer`red `driveToPose` in `Commands.parallel` with the intake (different subsystems, so L25's overlap idea reused for free), and `orElseGet(Commands::none)` makes "saw nothing" undramatic. **Measured detection error grows with distance — 10 mm at 1 m, 64 mm at 2 m, 129 mm at 3 m, 155 mm at 5 m** — and that table is the lesson's centre: `defer` commits to a *snapshot*, so the lesson presents commit / abort / look-again honestly, says the data favours look-again, and ships the simple version with Try It #3 building the good one. The rule to state is **data has a shelf life**. Verified end to end: 21 mm straight ahead at 2.5 m, 113 mm rotated 90° off-axis, nearest-piece selection correct with two balls, empty field yields no target.

[Lesson 28](lessons/28-aim-at-tag.md) makes the robot point itself at a tag, and **adds no new Java** — the lesson says so explicitly, per the plan's note that not every lesson needs to. New file `frc/robot/commands/Aim.java`: a `private Aim() {}` utility class like `Autos`, holding `tagPosition(int)` (`kTagLayout.getTagPose` → `Optional<Translation2d>`, so a typo'd ID is an empty rather than a crash), `headingToward`, `error`, `bearingRate`, `omegaToward`, `omegaTowardTag`, `isAimedAt`. **Static methods, not a command — that is why the driver binding and the BLine `"aim"` marker can share one implementation**; a command would have served exactly one caller. **`Aim` contains no camera anywhere, and that is the lesson's structural answer to "what if the tag isn't visible": nothing happens.** The tag layout is a file and the fused pose runs on odometry, so aim degrades with drift rather than failing — the first place L14's pose estimator visibly pays off. **No new `Drivetrain` code was needed**: `driveFieldRelative` has taken three suppliers since L10, so aim assist just swaps the third (`this::aimOmega`, bound to `leftTrigger().whileTrue(...)`, which interrupts the default drive command). `PathConstants.kAimTarget` is **deleted** and replaced by `kAimTagId = 20` (at (5.23, 4.03) on the 2026 field) plus `kAimTolerance`; `Autos.aimOmega` is deleted, `registerEventTriggers` gains a `Drivetrain` parameter, and `Autos` loses its `Rotation2d` import. **The lesson's centre is not what the plan predicted.** The plan expected camera *latency*; the dominant error is **P-control tracking lag against a moving bearing**, and latency is already handled by L14's timestamped `addVisionMeasurement`. Measured orbiting the tag at 3 m/s on a 3 m radius: **P only = 14.32° worst error, P + feedforward = 0.20°**, and the prediction matches exactly — the bearing moves at 1.0 rad/s and `error × kAimP` can only produce that from `1.0/4.0 = 0.25 rad = 14.32°`. The feedforward is `(vx·dy − vy·dx) / d²`, the cross product of field velocity with the offset to the target over distance squared, fed from `ChassisSpeeds.fromRobotRelativeSpeeds(drivetrain.getChassisSpeeds(), robot.getRotation())`. **This is the third instance of the course's feedforward rule** — `kG` for gravity and `kV` for speed in L18, bearing rate here — and the lesson states the general form: *a P term is for correcting, not sustaining; if a controller must produce output continuously just to hold station, calculate that output and supply it directly.*

[Lesson 29](lessons/29-flywheel.md) adds a shooter flywheel — the fourth mechanism on Lesson 13's spine, and **the first whose goal is a speed rather than a place**. `FlywheelIO` (`@AutoLog` inputs: velocityRps, appliedVolts, setpointRps, statorCurrentAmps; methods `setGoalRps`/`stop`) / `FlywheelIOTalonFX` (`VelocityVoltage` + `NeutralOut`, **no Motion Magic config at all** — a velocity goal has nothing left to profile) / `FlywheelIOSim extends` it (`FlywheelSim`, which unlike `ElevatorSim`/`SingleJointedArmSim` wants a `LinearSystem` from `LinearSystemId.createFlywheelSystem(DCMotor, J, gearing)`; only velocity is fed back, since a wheel has no position worth tracking) / a `Flywheel` subsystem. **`spinUp` deliberately does NOT `.until(...)`** — a position command can finish because arriving is a real event, but a flywheel that stopped asking would fall back to its default command mid-shot. **The centrepiece is that a model has a term for each thing the physics does, not a fixed set of four: there is no `kG` here**, and the lesson says writing one would be inventing a force. Direct drive (`kGearRatio = 1.0`, J = 0.01 kg·m²) so L18's arithmetic is visible: `kV = 12/100 = 0.12` V per rot/s and `kA = J × 2π × (12/7.09) = 0.106` V per rot/s², both reproducing the shipped constants. **Measured:** rest → 60 rot/s in 2.32 s, idle-30 → 60 in 1.24 s, holds 60.44 rot/s on ~7.2 V. **With `kV`/`kA` zeroed the wheel settles at 42.90 rot/s and stays there forever** — a *fixed point*, not a lag, and the prediction `goal·kP/(kP+kV) = 42.86` matches exactly; this is the starkest version of the course's feedforward rule (fourth instance). **The figure of merit is recovery time, not error**, and the lever is the idle speed rather than any gain: 0 → 2.32 s, 15 → 1.76 s, 30 → 1.24 s, 45 → 0.70 s, which is why `idle()` is the default command. **`kS` is discussed honestly and provably does nothing in this sim** — `FlywheelSim` has no friction term, and 0.05 V spins the simulated wheel to 0.37 rot/s; `kS = 0.15` ships as the true hardware value with a note that it's the one gain you cannot compute from a spec sheet. Spin-up shares the left trigger with L28's aim assist (different subsystems, so both run). **§5 draws a `Mechanism2d` speedometer** — the flywheel is the one mechanism with nothing physical to draw, so the picture is of the number: a square canvas, a centre hub, and **two** needles (actual and goal) so the gap between them is the error drawn to scale. The geometry is one expression, `angle = kZeroAngle − kFullSweep × (speed / kFreeSpeed)` = `−90° − 180° × fraction`, giving straight down at rest, straight up at full scale, positive sweeping the **left** half and negative the **right** (verified at 0/±50/100%); full scale is the motor's free speed and the fraction is **clamped**, because an unclamped needle wraps past vertical and looks like a modest negative speed — *a gauge that wraps is worse than no gauge, because it doesn't look broken*. Shooting speed sits at 60% of full scale. The dial updates live in a `updateDial()` helper called from `periodic()` purely so the lesson can present control and picture as separate contiguous pieces. **Deliberately omitted:** a shot-dip demo would need a sim-only hook on `FlywheelIO`, which is exactly the `GyroIO.setSimRotationRate` shape L16 deleted — recovery is taught as idle → shoot speed instead. **Testing trap:** Phoenix's simulated motors output nothing while the robot is disabled, so a bare motor+model rig reads 0.00 forever without `DriverStationSim.setEnabled(true)`.

[Lesson 30](lessons/30-current-limits.md) opens the "survives a match" arc with current limits and a deliberate brownout, and is the first lesson where **one subsystem's choices hurt another**. **Phoenix's simulated firmware genuinely enforces current limits** (measured: 200 A stator unlimited vs 21 A with a 20 A cap, and the wheel reaching 5.5 rot/s instead of 54.8) — so nothing here is narrated. **Phoenix's defaults are already ENABLED** — stator 120 A, supply 70 A, `SupplyCurrentLowerLimit` 40 A after 1.0 s — which reframes the whole lesson: it is not "add limits where there were none" but **"the defaults are per motor and the battery is per robot."** Measured on untouched defaults with identical loads: 3 motors → 108 A / 9.84 V (fine), **6 motors → 332 A / 5.37 V (brownout)**, 9 → 552 A, 12 → 751 A. Six motors is a swerve drivetrain plus two mechanisms, i.e. an ordinary second of a match. **Supply vs stator is measured, not asserted**: a Kraken at 12 V from rest holds stator pinned at 120 A while supply climbs 30 → 58 A as speed rises (applied 3.00 → 5.79 V), and `supply ≈ stator × (applied/battery)` reproduces both endpoints exactly — a stalled motor is terrifying for the windings and cheap for the battery, and a motor at speed is the reverse. All limits live in **one new `PowerConstants` class** (elevator 40 A, arm pivot 30 A, roller 20 A, flywheel 40 A, stator 80 A everywhere, brownout 6.3 V) rather than beside each mechanism, because a budget only means anything read as a set; the arm's roller had been getting a bare default config since L20 and now gets one too. `supplyCurrentAmps` joins the `@AutoLog` inputs (the arm gets two fields, one per motor), each subsystem exposes `getSupplyCurrentAmps()`, and **`RobotContainer` assembles the total** — no subsystem can, because none knows the others exist, which is the design working as intended. The battery model goes in **`Robot.simulationPeriodic()`** via `RoboRioSim.setVInVoltage(BatterySim.calculateDefaultBatteryLoadedVoltage(total))` — the same "shared world state" exception L16 used for the maple-sim arena, and the lesson names the precedent. **The loop closes for free**: every sim IO layer has fed `RobotController.getBatteryVoltage()` to its motors since L4, so lowering the rail immediately weakens everything. Brownout demo measured: no limits → 490 A / 2.09 V, defaults → 108 A / 9.84 V, the budget → 42 A / 11.16 V. **Scope:** the total sums the three mechanisms only; adding the drivetrain's eight motors is Try It #1. **Testing traps:** CAN IDs must be **≤ 62** (a rig on ID 70 silently failed a whole test with no output), and **`RoboRioSim` voltage is global state that survives across tests in the same JVM** — a battery-sim test leaves the rail sagged and silently corrupts any later test that reads `RobotController.getBatteryVoltage()`, which made a supply-vs-stator measurement read 23 A instead of 120 A until the rail was reset explicitly. The closing rule is that **a brownout never announces itself** — it looks like every subsystem breaking at once — so `Power/TotalCurrentAmps`, `Power/BatteryVolts` and `Power/BrownedOut` have to be logged before you need them.

[Lesson 31](lessons/31-alerts.md) gives the robot a pre-match checklist it runs on itself, using WPILib's **`Alert`** (`kError`/`kWarning`/`kInfo`). **Alerts publish to `/SmartDashboard/Alerts/{errors,warnings,infos}` as `string[]`** — AdvantageScope, Elastic and Shuffleboard render it with no wiring; the lesson uses only the default group so there is one place to look. **The framing beat is that logging a problem and reporting one are different jobs**: thirty lessons of logging built a complete record that nobody reads in a queue line. **`connected` goes in the `@AutoLog` inputs** (`motorConnected` on Elevator/Flywheel, `pivotConnected`/`rollerConnected` on Arm, `cameraConnected` on VisionIO) rather than being read ad-hoc, because it is a hardware reading and a replay is far more useful when the log knows the device was missing. Each subsystem owns the alerts about itself; **the battery alert lives in `Robot.robotPeriodic()`** on the same "nothing smaller knows about it" argument L30 used for the current total, with `PowerConstants.kLowBatteryVoltage = 11.5 V` chosen deliberately far above the 6.3 V brownout point — *an alert that fires when the problem is already happening has missed its job*. The camera alert puts the camera's name in the message because there are two of them. **`Alert.set(boolean)` is called every tick with the current answer, never "raised"** — an alert is a statement about now, so it must be able to clear itself. **What is demonstrable in sim, measured:** `TalonFX.isConnected()` reads false for ~240 ms after construction and true forever after, so the motor-disconnect alert cannot be made to fire at a laptop (the boot flicker is used instead as the clearest proof of the set-every-tick rule); `PhotonCamera.isConnected()` **is** honest, so renaming a camera in `VisionConstants` produces a real error alert and that is the hands-on demo; the battery alert works because L30 simulates the rail. **Testing trap:** `Alert` rides on SmartDashboard's sendable mechanism, which `IterativeRobotBase` pumps every tick — a bare JUnit test reads **empty** alert arrays unless it calls `SmartDashboard.updateValues()` itself.

[Lesson 32](lessons/32-testing.md) teaches students to write the JUnit tests this course has been using all along, and is **the first lesson whose snapshot ships test sources** (`code/lesson-32/tests/`). **The WPILib template already has everything** — JUnit 5, `useJUnitPlatform()`, and `wpi.java.configureTestTasks(test)` (the line that puts the HAL and sim libraries on the test classpath) — so **no `build.gradle` change is needed**; the student only creates `src/test/java/frc/robot/`. Two shipped tests, deliberately: `SuperstructureStateTest` (pure logic, no HAL, checks L24's transition table with loops a human could never press by hand) and `ElevatorHomingTest` (HAL + `DriverStationSim` + stepping the scheduler, checking L21's claim that a relative encoder reads zero at power-on and homing replaces the guess with a fact). The lesson teaches **arrange / act / assert** and makes the point that the *arrange* assertions do real work — without asserting the encoder is wrong and the switch disagrees, the final assertion would pass on a robot where homing did nothing. **`Elevator` gained `getHeightMeters()`** purely so the test has something to observe, and the lesson names that pressure: *you cannot assert on what you cannot observe, and being unable to write a test is usually the design telling you something.* **Both traps are measured, not described:** with 4 ms sleeps instead of the full 20, homing still "succeeds" but the final height reads **−0.34 m** (below the floor, physically impossible, looks exactly like a broken routine); and a second `Elevator` in a second test method throws **`AllocationException: Code: -1029`** because the first one's `DigitalInput` holds DIO 0 for the life of the JVM and `HAL.shutdown()` does not release it — hence one sequential scenario per subsystem, or per-test CAN IDs (≤ 62). The closing judgement is what to test: **claims a compiler can't check and a plot won't show you twice** — rules with many combinations, behaviours that fix something, and every bug you've already had once — and explicitly *not* constants, gains, or anything the compiler guarantees.

[Lesson 33](lessons/33-reading-a-log.md) is a skills lesson with **no new Java** — the technique, not the syntax, is the content — teaching forensic log-reading: find the moment a value changed, read the measurement and the decision built from it *together* rather than one at a time, and use replay (L13) to prove a fix against the exact match that already happened rather than a fresh guess. **The open decision from the plan doc (fixture log vs. student-generated) resolved as a third option**: a specific, contrived, student-generated scenario rather than either extreme — `ElevatorConstants.kTolerance` tightened by a decimal-place typo, `Centimeters.of(2)` → `Centimeters.of(0.002)`, verified in the sandbox rather than invented: the elevator's real Motion Magic settle error is a stable **~0.12 mm floor** (measured `1.1594621136490346E-4` m, flat across five further seconds of simulated time — a real floor, not still converging), so a 0.02 mm tolerance never trips `atGoal()`. **The bug is invisible in teleop by construction, not by narration**: `goToHeight` already ends in `.until(this::atGoal)`, so a button binding just re-triggers a fresh command on every press — a command that never finishes is indistinguishable from one that does unless something else is sequenced *after* it with `.andThen(...)`, which only happens in autonomous. That's the whole "worked on the bench, failed on the field" story, and it falls straight out of code the student already has rather than needing an invented excuse. **The fix, `Centimeters.of(0.1)` (1 mm), was also verified** (~8.6× margin over the measured floor), and replaying the same recorded log through the fixed code is the lesson's central demonstration: `Elevator/AtGoal` sits false the whole session in `RealOutputs` and flips true at the correct tick in `ReplayOutputs`, computed for a match that already happened — L13's "recompute the whole match" made concrete as a debugging tool rather than a demo. **`Elevator/HeightErrorMeters` (signed) is the one permanent code change**, closing the gap where the log already had the decision (`AtGoal`) and the raw measurements but not the number that explains the decision — named as the standing rule: a number computed by eye off two plots belongs in the log, not in your head. **A second, faster example is narrated rather than hands-on** — a BLine `lib_key` case mismatch (`"intake"` vs `"Intake"`, a GUI-authored path-file edit, not a Java constant) — deliberately reusing Lesson 17's already-established "an unknown key logs a warning and keeps driving" behavior rather than re-verifying it, so the second worked example demonstrates the method generalizes rather than repeating the first bug's flavor. Lesson 32's send-off became a forward handoff.

[Lesson 34](lessons/34-tuning-with-sysid.md) closes the plan doc's current arc, meeting a real machine after thirty-three lessons of spec-sheet-derived gains. **The open decision (how much is code vs. procedure) resolved as a clean split**: §2 (safe first power-on) is pure checklist, opening with "This section has no code in it" so the reader never mistakes judgment for something a compiler checked; everything else is code, verified for real. `SysIdRoutine`/`Config`/`Mechanism`/`Direction`/`SysIdRoutineLog.MotorLog`'s exact constructors and defaults were **read out of the actual 2026.2.1 jars with `javap`, not guessed** — `Config()`'s defaults are 1 V/s ramp, 7 V step, 10 s timeout, confirmed straight from bytecode. **The flywheel (L29) was the deliberate mechanism choice** for a second reason beyond "L29 already exists": it has no position to get wrong — no floor, no hard stop — making it the safer mechanism to hand raw open-loop voltage to, which the lesson states outright rather than leaving as an accident of sequencing. **`FlywheelIO.setVoltage` mirrors `ElevatorIO.setVoltage` from L21's homing** — same "open loop because closed loop is exactly what you don't trust yet" reasoning, and `FlywheelIOSim` needs zero changes, inheriting it the same way it inherits `setGoalRps`. **The central finding is measured, and richer than the outline predicted**: characterizing the flywheel with `SysIdRoutine.Config()` left at its defaults gives **`kS` ≈ 0.89 V** in this course's own simulated run — nearly 6× the shipped `0.15 V` — not because the model is wrong, but because the default 1 V/s ramp is too fast for a small, direct-drive flywheel to stay quasi-static, so the quasistatic test partly measures its own ramp rate. Slowing the ramp to **`Config(Volts.of(0.25).per(Second), Volts.of(7), Seconds.of(30))`** drops measured `kS` to **≈0.23 V**; `kV` recovers accurately either way (≈0.12, matching the model), which is the tell that the *test*, not the mechanism, was the problem. **This is real SysId methodology, not a sim-only quirk** — a too-fast ramp corrupts `kS` on real hardware exactly the same way, since it's a property of a first-order system responding to a ramp input, not a simulation artifact. §7 is honest about the one thing that *is* sim-specific: `FlywheelSim` has never modeled friction (L29 proved this by hand), so even the corrected 0.23 V isn't "the friction sim found" — it's the residual of a ramp-rate artifact on a mechanism whose true simulated `kS` is exactly zero, which the lesson states plainly rather than implying agreement it can't back up. **`SysIdRoutineLog` writes through WPILib's own `DataLogManager`, not AdvantageKit's `Logger`** — confirmed via bytecode that `getLog()` lazily auto-starts `DataLogManager` on first use, landing in the *same* `logs/` folder AdvantageKit already uses in sim, but as a **second, separate `.wpilog` file** — a genuinely easy thing to trip over unwarned, so the lesson calls it out by name. Bindings are two-button combos (`back+y`/`back+a`/`start+y`/`start+a`) using `Trigger.and(...)` from L22, so a characterization command can't be tripped by one accidental press — the same reasoning L21 used putting homing on its own button. **§7 covers characterizing a mechanism with finite travel**, and its three findings are measured: **Phoenix soft limits DO stop an open-loop `VoltageOut`** (6 V for 4 s against a 1.5 m limit: **2.503 m** without, **1.505 m** with, 0.000 applied volts), so L20's arm soft limits protect a SysId run while L18's `clampToTravel` does nothing — it clamps a *goal*, and open loop never sets one, which is why `code/lesson-34/` also ships `ElevatorIOTalonFX.java` with soft limits the course had only ever put on the arm. **The slower ramp from §6 makes travel worse, not better** — distance to reach 6 V is **1.568 m at 1.0 V/s, 3.158 m at 0.5 V/s, 6.469 m at 0.25 V/s**, so halving the rate doubles the distance and §6's own 0.25 V/s would need 6.469 m of an elevator that has 1.5 m; the lesson presents this as a real tension resolved by giving up voltage range rather than ramp rate. **Lowering the dynamic step voltage is the fix for the step test** (travel in 1.5 s: **1.010 m at 7 V, 0.561 m at 4 V, 0.268 m at 2 V** — the default 7 V eats two-thirds of the elevator's travel against a 10 s default timeout). **A trap worth not rediscovering: none of this is demonstrable in this course's own sim.** `ElevatorIOSim` builds `ElevatorSim` with `kMinHeight`/`kMaxHeight`, so the *physics model* is a wall at 1.5 m — the real sim elevator driven open loop into the top stopped at exactly 1.500 m while the encoder had only reached **1.150**, under the 1.5 threshold, proving the limit never fired and the model stopped it. Observing the firmware limit at all required widening the rig's model bounds to ±20 m. The lesson says so directly, as an early arrival of §8's theme. The "home it first" callout is likewise **derived from L21's already-measured encoder-offset fact, not freshly measured**, since sim can't show that either. **Lesson 34 is now the lesson that ends with a send-off and no `Next:` link**, closing out the plan doc's current arc.

## Asides (out-of-sequence lessons)

Alongside the numbered sequence, `lessons/aside-*.md` files hold
supplementary lessons that aren't part of the linear build (e.g.
[aside-debugger.md](lessons/aside-debugger.md)). They follow the same
voice and template as numbered lessons but:

- Do **not** have a `Next:` link at the bottom (they're not in a chain).
- **May reference numbered lessons for examples** — treat those as "you can
  read this any time after Lesson N," not "this must come before Lesson N+1."
- Are linked from the **Asides** section in
  [lessons/README.md](lessons/README.md), not the main lessons
  table.
- **An aside that has nothing WPILib-version-specific in it (git-branching,
  debugger) is shared between both tracks** — one file, lives under
  `lessons/`, linked from both `lessons/README.md`'s and
  `../docs/lessons/v3/README.md`'s Asides sections. An aside whose content
  genuinely differs per track (setup: different install/project-creation
  steps; odometry-thread: needs AdvantageKit, which the OpMode track
  doesn't have) gets its own `../docs/lessons/v3/aside-<slug>.md`, linked only
  from that track's page, and should reuse as much of the classic version's
  text as still applies rather than rewriting it from scratch.

**An aside may ship code**, in `code/aside-<slug>/`, applied *on top of* a named
lesson rather than rolled through in order:
`./2026/tools/verify-lessons.sh 16 aside-odometry-thread`. The base lesson is
explicit and not guessed, because an aside's snapshot is written against one
lesson's version of the files it touches — applying it over a later lesson would
revert everything that lesson changed in those same files. For the same reason an
aside must **not** ship `Constants.java` or any other file the linear build keeps
editing; put constants the aside needs in the aside's own new class.

[aside-odometry-thread.md](lessons/aside-odometry-thread.md) converts the
drivetrain to the full AdvantageKit shape: an `OdometryThread` sampling drive,
steer and gyro signals at 250 Hz via `BaseStatusSignal.waitForAll`, timestamped
samples in the `@AutoLog` inputs, and `estimator.updateWithTime` replacing
`estimator.update`. **Its headline finding is negative and measured, and the page
leads with it**: 250 Hz odometry is *not* meaningfully more accurate than 50 Hz.
WPILib integrates a constant-curvature arc exactly, so on smooth motion the error
difference is **0.000000 m at both rates**; only changing curvature breaks the arc
assumption, and an aggressive slalom (4 m/s, ±3 rad/s) gives **1.7 mm at 50 Hz vs
0.1 mm at 250 Hz** — 26.7× better, of a number already dwarfed by the centimetres
of wheel slip Lesson 16 made visible. The real reasons given are coherent
snapshots (`waitForAll` refreshes every signal together, instead of five reads
smeared across a loop), finer timestamp resolution for L14's vision rewind, and
being able to read the AdvantageKit template. **Verified end to end in sim**:
Phoenix's simulated firmware really does publish at the requested rate, and the
real `Drivetrain` collects **5.2 samples per 20 ms tick** (max 6, zero empty
ticks) — the wobble being exactly why samples carry timestamps. The page is
honest that sim physics still only advances at 50 Hz, so the extra samples
faithfully describe motion computed at 50 Hz. **The change is additive**: a
`samples == 0` branch falls back to Lesson 14's single `estimator.update`, so
Lessons 17–34 neither need it nor break with it, and the entire upgrade lands
inside `Drivetrain.updatePoseEstimate` — the payoff of L14's `PoseProvider`
interface. Threading content is the real teaching load: `ReentrantLock` with
`try`/`finally`, holding one lock across the gyro *and* all four modules so the
snapshot can't be stitched from two instants, bounded `ArrayBlockingQueue` so a
stalled main loop drops samples rather than exhausting memory, `setDaemon(true)`,
and `volatile` with its narrow guarantee. The `Drivetrain` constructor exists only
to `start()` the thread after every field initialiser has registered its signals.
